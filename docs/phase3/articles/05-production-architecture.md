# From Voice AI Demo to Production-Ready Architecture

A convincing voice demo proves that a user can have a conversation under some conditions. A production system must also decide who is allowed to act, what happens when a source is wrong, how spending stops and which evidence is retained. These responsibilities belong to the system around the model.

Consider a fictional shipment lookup. The model might correctly select `lookup`, but that does not authorize access to another customer's record. Authentication establishes the caller; authorization establishes which records and actions that caller can access. Tool input validation bounds the request. Output validation prevents a malformed or mismatched source record from becoming a confident answer. Prompt wording is not a substitute for these controls.

The [workshop starter](../../../community/elevenlabs-belgium/starter/agent.mjs) demonstrates a narrow part of this boundary. A missing reference clarifies; an invalid reference is rejected before the tool runs; an unknown record produces no invented answer; a source exception recovers honestly; a mismatched response escalates. Its eight tests are deterministic business-contract tests. They do not emulate speech or establish LLM compliance.

AgentProof uses a deliberately smaller public surface. It is a static application with sanitized synthetic evidence, no provider credentials, no live-generation routes and no analytics. A visitor can inspect failures and download evidence without creating a billing liability. Feedback remains in the tab until the user downloads it; it is not silently sent to a collection service. No external participants or adoption have been claimed.

That architecture makes the demonstration useful while reducing its authority. It does not create a production live-testing service by implication. Such a service would need authenticated project membership, server-only credentials, allowlisted test and tool identifiers, bounded input sizes and timeouts, rate limits, per-user quotas and shared-account reservation controls. Public errors should be safe; private logs should be structured and redacted. Retries need an explicit billing and side-effect policy.

Data retention needs similar precision. Committing synthetic transcripts is different from retaining real conversations. A future pilot should collect the minimum useful notes, avoid recording by default, set a retention period and provide a real private deletion route before recruiting people. Deleting a file from the working tree does not erase Git history or other people's clones. Never promise deletion guarantees the architecture cannot deliver.

Operational observability should distinguish facts from inferences. A configuration fingerprint identifies a redacted snapshot, not every secret or downstream service setting. A tool trace shows observed calls, not whether a business action was lawful. A text evaluation does not measure microphone recognition, interruption behavior or perceived voice quality. These limitations should travel with exported evidence instead of being hidden in a distant disclaimer.

The [threat model](../threat-model.md) lists current mitigations and missing conditions. The [integration plan](../integration-plan.md) defers shared deployment changes until the parallel session is reconciled. This work is a tested pilot candidate, not a declaration of production certification. The practical next step is controlled user evaluation and a separately designed live service only if that validation establishes a useful need.
